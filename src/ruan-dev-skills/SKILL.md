# Ruan Dev Skills 2.0

把「需求材料 + 当前真实代码」编译成可追溯、可恢复、低上下文成本的 AI 接力开发资料。一次调用只负责初始化或调整资料；后续业务开发由产出的《开发协议》和《开发接力提示词》约束。

## 硬边界

- 只写 `docs/AI dev docs/` 资料仓；可读代码仓用于事实核验。
- 不修改业务源码、测试、数据库、运行配置或开发环境。
- 不实现需求，不安装依赖，不执行环境修复，不代替后续开发会话运行 S001。
- 不扫描、识别、脱敏或拦截秘密、Token、凭据和隐私材料；调用前由调用方承担原样归档风险。
- 不建立锁、后台协调器、跨仓事务、需求数据库或复杂状态机。
- 严格串行：同一时刻只允许一个开发会话写代码仓或资料仓。

## 输入

需要两个参数：

1. 需求材料：一个真实文件或真实目录。
2. 版本目录 `<V>`：`<项目总目录>/docs/AI dev docs/<版本号>/`，由调用方明确指定。

版本号不生成、不推断、不替用户升级。`<V>` 的父目录必须正是 `AI dev docs`；代码仓是当前工作目录所在的独立 Git 根；资料仓 `<R>` 是 `<V>` 的父目录，也必须是独立 Git 根。

需求源安全边界：

- canonical path 不得位于 `<R>` 内；
- 不得从 `<V>`、`plans/` 或整个资料仓再次摄取；
- 输入本身不得是符号链接；排除输入目录自身 `.git/` 后，内容不得含符号链接；
- 需求目录不得含空目录；Git 无法单独追踪空目录，调用前提供显式占位文件。
- 不满足边界时停止，要求提供真实文件或真实目录。

## 固定资产

以下文件是 Skill 自带资产，生成时原样复制，不按业务需求改写：

- `assets/relay-prompt.md` → `<V>/开发接力提示词.md`
- `assets/dev-protocol.md` → `<V>/开发协议.md`

后续业务需求变化不得修改两个固定资产；协议升级必须由未来明确的 Skill 版本迁移处理。

## 机械辅助脚本

脚本路径记为 `<SKILL>/scripts/devdocs.py`。命令中的所有路径加双引号。

| 命令 | 用途 |
|---|---|
| `check-root --root "<R>" [--init] --code "<C>" --version-dir "<V>"` | 校验双仓边界，返回代码 HEAD、dirty 状态和代码相对路径 |
| `archive --root "<R>" --version-dir "<V>" --source "<需求源>" --label <简述>` | 分配 P-ID、复制需求、拒绝边界错误、生成清单并做字节校验 |
| `verify --root "<R>" --plan-dir "<Pxxx目录>"` | 提交后验证 Pxxx、清单和 Git 跟踪状态 |
| `same --source "<需求源>" --plan-dir "<Pxxx目录>"` | 判断恢复时输入是否与已归档快照一致 |

机械脚本失败时，根据 JSON/错误信息处理；不绕过边界检查，不向调用方暴露 Python traceback 作为主要交互结果。

## 模式判定

先检查 `<V>` 和资料仓 HEAD：

- `<V>` 不存在或为空：初始化。
- 资料仓存在但没有任何 commit：按空资料仓初始化，不把不存在的 HEAD 当作 checkpoint。
- 可识别协议 + 已提交状态 `初始化中`：恢复初始化；已有 Pxxx 不重新摄取。
- 可识别协议 + 已提交状态 `调整中`：恢复同一轮调整；同一输入用 `same` 确认后继续。
- 可识别协议 + `可接力` 或 `已结束`，且提供新需求：调整。
- 可识别协议 + `可接力` 或 `已结束`，未提供新需求：告知当前无资料调整任务。
- 有内容但没有协议标识或固定资产不齐：停止并让调用方选择覆盖、改名或中止；绝不自动修复或覆盖。

如果工作树状态显示 `初始化中`/`调整中`，但 HEAD 中没有对应已提交状态，先识别未完成的 Pxxx 和骨架。只允许删除明确未提交的摄取残留；不得删除已提交 Pxxx，不得混合新旧两轮需求。

## 初始化流程

1. 检查资料仓、代码仓和 dirty 状态；资料仓不存在时可在明确的 `AI dev docs` 根执行 `git init`。
2. 创建 `<V>` 和最小《步骤总览》骨架，状态为 `初始化中`。
3. 用 `archive` 摄取 P001；归档内容必须通过字节校验、符号链接检查、`归档清单.json` 生成和 Git 忽略检查。
4. 将骨架、P001、`plans/索引.md` 和清单提交为资料仓摄取 checkpoint；提交成功后 P001 才正式成立。
5. 只读取 `plans/P001/` 副本完整理解有效需求，按需核验真实代码、测试和配置。
6. 在 `plans/索引.md` 建立需求关系表和轻量需求覆盖摘要：`需求锚点 → S-ID / 无需开发及原因`。
7. 生成 S001（环境确认与原始基线建立）和 S002 详档，远端步骤只保留粗粒度目标与验证观察点。
8. 生成《当前状态》《开发环境》《步骤总览》、步骤文件和必要的《决策记录》，复制两个固定资产。
9. 自检通过后将状态改为 `可接力`，提交资料仓 checkpoint。不要在本次调用中开始业务开发。

## 需求调整流程

1. 先把已提交总览状态改为 `调整中`，形成可恢复资料状态。
2. 摄取新 Pxxx；旧 Pxxx 永不修改、移动、覆盖或重新编号。
3. 用 `plans/索引.md` 明确增量、修订、全量替换和覆盖范围。位置写成 `P-ID + 归档内相对文件 + 稳定位置`；文本可用行号/标题，PDF 可用页码，无法细分时使用文件级引用和极短语义说明。
4. 部分修订只覆盖明确写出的文件和位置，未覆盖部分继续沿用旧 P-ID。无法可靠判断补充与替换且业务结果不同，暂停询问。
5. 校验受影响 Pxxx 的 `归档清单.json`；清单与副本不一致即视为需求证据完整性冲突，停止规划。
6. 同时对账当前有效需求、真实代码和当前计划：已完成步骤保持 `已完成`；重复修改新增 S-ID；只有原 DoD 证据不足才标 `需复核`；未开始步骤可保留、修改、废弃或插入，但旧 S-ID 不重编号。
7. 当前代码存在半成品时只记录保留继续、前向调整或撤销的处置决定；本 Skill 不修改业务代码。
8. 更新覆盖摘要、受影响步骤、总览和当前状态；自检通过后改为 `可接力` 或 `已结束`，提交资料仓 checkpoint。

## 规划原则

- 事实分层：`plans/` 定义需求目标，真实代码定义现状，《步骤总览》定义计划，《当前状态》定义执行指针，《开发环境》定义环境事实。
- 代码优先：涉及“现在是什么”必须核验真实代码，不能只信需求或旧计划。
- 披露式读取：当前状态 → 当前步骤 → 步骤所需资料 → 相关代码 → 按需扩展。
- 一个步骤应能在一个 fresh context 内完成必要访读、实现、验证、修复和回写；不要按技术层机械切分。
- 只有近期步骤详拆；远端步骤不猜未来文件、类、函数或行号。
- S-ID、P-ID 单调递增、永不复用；需求变化前向修正，默认不回滚。
- 需求覆盖摘要只做索引，不复制需求正文，不成为第二套需求来源。

## S001 语义

S001 对代码仓原则上只读。可查看环境、代码和配置，执行不会修改已跟踪文件的构建与测试，使用命令级临时环境变量，并更新资料仓的《开发环境》和基线信息。

不得为让测试跑通而修改业务源码、测试、构建配置或 `conftest.py`。若必须修改代码仓：先记录原始失败，生成独立环境/测试基础设施步骤，由后续开发会话完成；修复完成后再建立可用开发基线。必须区分项目原始状态与修复后的开发起点。

## 完成与恢复

后续开发由《开发协议》驱动，每个会话只推进一个步骤。验证通过后先形成代码 checkpoint，再把准确的代码 commit hash 写入资料；无代码变化记录当时 HEAD，不制造空 commit。hash 是完成步骤的强证据，`版本号 + S-ID` 只作 hash 失效后的辅助搜索；多个候选必须结合基线、diff、验证结果和真实代码重新核验，不能自动猜测。

预存 dirty workspace 记录路径、文件大小和 SHA-256。若当前步骤修改、删除或重命名同一路径，且无法区分预存内容与当前内容，不得把该路径自动纳入 checkpoint，应保留现场并暴露冲突。

## 完成前自检

至少确认：双 Git 根正确；协议和状态正确；Pxxx、清单和 Git checkpoint 完整；需求源不在资料仓且无符号链接、无空目录；需求覆盖摘要无漏项；相关代码已核验；S001 保持代码仓只读；当前指针唯一；S/P ID 未复用；近期步骤可执行；固定资产未漂移；代码 checkpoint hash 准确。

## 最终回复

完成后只输出四段：

1. 模式：初始化 / 调整。
2. 产出位置：`<V>` 绝对路径。
3. 关键摘要：步骤数、当前步骤、待澄清项数量、决策记录数量。
4. 后续操作：使用 `<V>/开发接力提示词.md` 新开会话推进。

不要在最终回复中展开完整文档内容。
